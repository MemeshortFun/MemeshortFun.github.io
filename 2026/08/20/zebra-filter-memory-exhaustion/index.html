Unauthenticated Memory Exhaustion in Zebra's Tracing Filter Endpoint

2026-08-20 Updated 2026-08-20
#security #denial-of-service #zebra #zcash

Zebra’s tracing configuration endpoint can become a remote denial-of-service primitive when it is exposed beyond a trusted local interface. An unauthenticated attacker can submit an oversized POST /filter request, causing the node to hold and parse the request body in memory. In testing, a 38 MB request grew the zebrad process to roughly 1,981 MB before the operating system’s out-of-memory killer terminated it.

The issue is configuration-dependent, but the impact is serious for an affected deployment: the node can become unavailable, and other services sharing the same host may also be killed or destabilized.

What the endpoint does

The /filter endpoint is part of Zebra’s tracing and filter-reload functionality. It is not enabled in a default installation. The relevant attack surface appears when Zebra is built with the filter-reload feature and tracing.endpoint_addr is configured to an address reachable by an attacker.

In the affected implementation, read_filter() in zebrad/src/components/tracing/endpoint.rs reads a POST /filter body with collect().await. There is no effective request-body size limit before the complete body is held in memory. The body is then parsed as a filter string, which adds another layer of allocation and produces an observed memory amplification of approximately 12x.

Attack path

The attack requires no credentials and can be carried out with an ordinary HTTP request:

  1. Connect to the externally reachable tracing endpoint.
  2. Send a large body to POST /filter.
  3. Let Zebra collect and parse the entire request in memory.
  4. Continue sending requests or use a sufficiently large body until the host reaches memory pressure.
  5. The operating system’s OOM killer terminates zebrad, and possibly other processes on the host.

The report’s test environment used Zebra v6.3.0 with filter-reload enabled. A 38 MB request increased resident memory to approximately 1,981 MB, after which the connection was interrupted and the process disappeared. A restart does not remove the exposure: while the endpoint remains reachable, the same request can be sent again.

A second security problem: unauthenticated writes

The endpoint is not limited to oversized reads. Unauthenticated users can also change logging filters through POST /filter. For example, an attacker can set filters such as zebrad=trace or zebra_network=trace without a token or login.

That capability is independently problematic. Trace-level logging can consume substantial CPU, disk, and memory, while also diluting useful audit records. It can therefore serve as a preparatory step before the memory-exhaustion request, increasing pressure on the host and making incident analysis harder.

Conditions that limit or increase the risk

Default installations are generally unaffected because the feature is not enabled and the endpoint is not configured. Binding the endpoint to a local-only address, such as 127.0.0.1, also prevents a direct remote connection.

The risk increases when:

  • Zebra is compiled with --features filter-reload;
  • tracing.endpoint_addr binds to an externally reachable address and port;
  • the endpoint is exposed without authentication or authorization;
  • there is no request-size limit or process-level memory cap; and
  • unrelated services share the same host.

The vulnerability is primarily an availability issue. The report does not demonstrate theft of funds, disclosure of confidential data, or manipulation of blockchain consensus. However, the OOM killer chooses which process to terminate, so the blast radius can extend to databases, wallets, monitoring agents, or other co-hosted services.

Recommended remediation

The most direct fix is to reject oversized request bodies before they are fully buffered. A hard Content-Length check should be combined with a streaming limit while reading, returning HTTP 413 Payload Too Large when the limit is exceeded. Relying on Content-Length alone is insufficient because clients can omit it or use a streaming transfer mode.

The endpoint should also require authentication and authorization. Binding it to loopback by default is a useful deployment safeguard, but it should not replace access control when remote administration is genuinely required. The filter string itself needs a length limit and validation as well.

Operational defenses can reduce the blast radius while code fixes are being prepared:

  • keep the endpoint off public interfaces;
  • place it behind an authenticated reverse proxy when remote access is necessary;
  • apply a cgroup or systemd memory limit to zebrad; and
  • monitor for unexpected filter changes, large POST bodies, and OOM-killer events.

Regression tests should verify that oversized bodies are rejected while the process remains alive, unauthenticated requests cannot read or change filters, and valid authenticated filter updates continue to work.

Takeaway

This incident illustrates why operational endpoints deserve the same security review as public APIs. A feature intended to make tracing convenient combines three dangerous properties when misconfigured: unauthenticated access, unrestricted request buffering, and the ability to increase logging verbosity. The result is a simple remote path to node termination.

For Zebra operators, the immediate action is straightforward: do not expose the tracing endpoint to untrusted networks. For maintainers, bounded streaming reads, authentication, input validation, and regression coverage should make the endpoint’s resource usage and trust assumptions explicit.
