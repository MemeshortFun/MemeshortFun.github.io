How Zebra's Mempool Crawler Bypasses the Per-Peer Download Limit

2026-08-20 Updated 2026-08-20
#security #denial-of-service #zebra #zcash

Zebra limits concurrent transaction downloads to protect its mempool. The global limit is 500 slots, and the normal per-peer limit is five. A flaw in the mempool crawler path allows one ordinary P2P peer to bypass the per-peer limit and fill all 500 global slots with fake transaction IDs.

The node does not crash, and CPU and memory usage can remain normal. The failure is quieter: legitimate transactions are rejected with FullQueue, so transfers may remain unconfirmed, merchants may not receive payment confirmations, and miners may build templates without transactions that would otherwise be available.

The issue affects zebrad v6.3.0 and was also reproduced against historical versions 6.2.2 and 6.2.3. The report states that zcashd is not affected.

The intended protection

Zebra’s download pipeline has two relevant quotas:

The global limit prevents download and validation work from exhausting host resources. The per-peer limit prevents one peer from occupying the entire global pool. It was introduced to address an earlier class of transaction-download abuse.

The protection depends on the download request carrying the address of the peer that supplied the transaction. When that source is present, Zebra can count pending downloads for that peer and return FullQueue after the fifth item.

Where the crawler differs

The normal broadcast path preserves the source peer:

The crawler path is different. Zebra proactively asks a selected peer for its mempool transaction list. The response is queued with source=None, even though the crawler knows which connection supplied the response:

The if let Some(source) guard means that no per-peer accounting occurs when the source is None. A single crawler response can therefore inject thousands of IDs, while the global pool admits the first 500. Every later legitimate transaction encounters a full queue until slots are released.

Attack timeline

The attack only requires an ordinary P2P connection. No account, special privilege, or mining power is needed.

In the reported reproduction, the crawler selects three peers at random approximately every 73 seconds. When it selects the attacker’s connection, the attacker responds to the mempool request with about 5,000 fake transaction IDs and does not complete the subsequent getdata requests.

The resulting sequence is:

  1. The crawler selects the attacker’s peer.
  2. The attacker returns thousands of fake transaction IDs.
  3. The crawler queues the IDs without a source peer.
  4. All 500 global download slots become occupied.
  5. Legitimate transactions receive FullQueue and cannot enter the mempool.
  6. Download timeouts release slots after roughly 20 seconds.
  7. The next crawler cycle can fill the slots again.

With a single IP, selection is probabilistic and the disruption is intermittent. Because the default max_connections_per_ip is one, multiple cooperating IP addresses increase the attacker’s coverage. The report estimates that approximately 15 IPs can approach nearly continuous selection, although this is not a one-request permanent outage.

Why previous fixes do not close this path

The crawler bypass remains after two related hardening changes. One fix limits per-peer work when a source peer is present. Another charges actively pushed full transactions or transaction messages against the per-peer budget. Both protections work on paths that pass Some(peer).

The crawler explicitly passes None, so the guard bypasses both the accounting and the associated overload behavior. The code also treats crawler traffic as an intentional exemption without adding a compensating total limit for each crawler response or cycle.

That design creates a mismatch: the global pool is bounded at 500, but a single crawler response can attempt to populate the entire pool. A peer that repeatedly refuses the resulting getdata requests is not necessarily marked as misbehaving, and the crawler path does not consistently surface FullQueue as an overload signal.

Observed impact

The report reproduced the issue in an isolated Regtest environment with Zebra v6.3.0. During saturation:

  • mempool_currently_queued_transactions reached 500;
  • the per-peer full-queue metric did not appear, consistent with the skipped source check;
  • the fake peer log showed 5,000 returned transaction IDs; and
  • Zebra remained alive with stable memory and approximately 0.1-0.2% CPU.

This is an availability vulnerability, not a memory-exhaustion crash. It does not directly steal funds, alter existing blocks, corrupt on-disk state, or change consensus. The practical damage is transaction propagation failure and delayed confirmation.

The impact can reach multiple user groups. Wallet users may see transfers appear to vanish, merchants and payment gateways may wait indefinitely for confirmations, exchanges may experience delayed deposits and withdrawals, and miners may omit fee-paying transactions from block templates. Attacking several nodes at once could turn local transaction delays into broader propagation problems.

Recommended remediation

The crawler should preserve the source peer when it queues transaction IDs. The peer address is already known because the crawler initiated the connection, so the request should carry Some(peer) into download_if_needed_and_verify. This makes the existing per-peer cap apply naturally.

Additional defenses should make the crawler safe even if source tracking fails again:

  • impose a separate, substantially smaller transaction enqueue budget per crawler response and cycle;
  • associate repeated failed downloads with the supplying peer and apply misbehavior scoring or bans;
  • propagate FullQueue through the crawler path and disconnect peers that repeatedly inject unusable transaction IDs; and
  • remove or narrow the explicit crawler exemption instead of relying on a design comment as a security boundary.

Regression tests should cover both the ordinary and crawler paths:

  1. Confirm that the existing broadcast path still enforces the five-transaction per-peer limit.
  2. Return more than 500 fake transaction IDs from a crawler response and verify that one peer cannot occupy more than the configured per-peer quota.
  3. Verify that the per-peer counter records crawler downloads under the supplying peer.
  4. Confirm that a peer refusing getdata is assigned misbehavior and can eventually be banned.
  5. After saturation recovers, verify that legitimate transactions enter the mempool normally.

Takeaway

Resource limits are only effective when every path that consumes the resource carries the identity and accounting context used by the limit. Zebra’s normal transaction path preserves that context; the crawler path discards it. The result is a bounded but meaningful denial of service in which the node looks healthy while refusing the transactions its users need.

For operators, keeping peers and node versions monitored remains important, but configuration alone cannot reliably eliminate this code-path issue. For maintainers, preserving the source peer and adding crawler-specific budgets and overload handling are the key repairs.
