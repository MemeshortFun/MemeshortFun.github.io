Unauthenticated Zakura RPC Exposure Can Exhaust Node Resources

2026-08-21 Updated 2026-08-21
#security #zakura #rpc #denial-of-service #zcash

Zakura 1.2.0 can expose administrative RPC methods to unauthenticated remote callers when two settings are combined: the RPC listener is bound beyond loopback, and cookie authentication is disabled. In that deployment, an attacker who can reach the RPC port can request expensive history scans and large address collections without credentials.

The requests can consume node CPU, memory, and disk I/O. Repeated or concurrent calls can compete with peer synchronization, state management, and mempool processing, degrading RPC responsiveness and potentially making the node unavailable.

This is a configuration-dependent resource-exhaustion issue. Default installations are substantially safer because cookie authentication is enabled and the listener is restricted to loopback.

Vulnerability at a glance

The report identifies the affected product and version as:

  • Product: Zakura / zakurad
  • Version: 1.2.0
  • Status: published
  • Weakness classes: CWE-400, uncontrolled resource consumption; CWE-770, allocation of resources without limits or throttling; and CWE-306, missing authentication for a critical function

The dangerous configuration has four requirements:

  1. RPC listens on a non-loopback address.
  2. Cookie authentication is disabled.
  3. The attacker can reach the RPC port.
  4. The attacker submits very large scan ranges or address collections.

When all four conditions are met, administrative methods become anonymous high-cost work queues.

What normal behavior should look like

Administrative RPC should be authenticated and available only to trusted networks. Expensive methods should also enforce explicit bounds on the requested range, number of addresses, result size, and concurrency.

The abnormal behavior is the inverse: a caller can request work far larger than the request itself suggests, and multiple requests can run at the same time against the same node resources. A small JSON-RPC request can therefore trigger a full-chain scan or collect a very large result set.

The call chain

The exposure begins during RPC setup. Authentication middleware is loaded only when enable_cookie_auth is true. If it is false, the server does not add the cookie-auth layer. Configuration validation does not reject the combination of a non-loopback listener and disabled authentication.

Root causes

1. A high-risk configuration is accepted

Disabling cookie authentication removes the protection, but the configuration does not reject or strongly warn when RPC is simultaneously bound to a non-loopback address. This turns an administrative interface into a remotely reachable anonymous endpoint.

2. History scanning has no practical upper bound

Impact and limitations

Sustained requests can degrade RPC responsiveness and compete with synchronization, peer, and mempool work. Because the RPC process shares host resources with core node services, the operational impact depends on chain size, index size, storage speed, available memory, and request concurrency.

The issue does not by itself demonstrate fund theft or consensus corruption. It is primarily an availability and resource-isolation problem. Several factors reduce risk: cookie authentication is enabled by default, loopback binding blocks anonymous remote access, and network firewalls or an authenticated reverse proxy can prevent reachability.

The separate sendrawtransaction retry-channel issue mentioned in the source report is outside the scope of this analysis.

Remediation

The safest short-term deployment posture is to keep RPC on loopback or an authenticated private network. Do not disable cookie authentication on a listener reachable by untrusted clients. A reverse proxy can add network-level access control while a code fix is prepared, but it should not be treated as a substitute for application-level authentication.

Longer-term fixes should include:

  • reject startup when RPC is non-loopback and authentication is disabled, or require an explicit high-risk override;
  • clamp num_blocks to a documented safe maximum and return a controlled error for oversized values;
  • limit address count, height span, result size, and concurrent expensive requests;
  • paginate large result sets instead of collecting them without a bound; and
  • update configuration examples to show the safe authenticated deployment.

Regression tests should verify every listener and authentication combination, including IPv4 and IPv6 wildcard addresses. They should also confirm that huge num_blocks values fail quickly, address queries enforce count and range limits, result sizes are bounded, and bounded RPC calls remain responsive while peer synchronization and mempool processing continue.

Takeaway

Authentication and resource limits solve different problems, and an administrative API needs both. Zakura’s default settings provide meaningful protection, but accepting a remotely exposed listener with authentication disabled creates a direct path from an anonymous request to expensive backend work.

For operators, the immediate control is simple: bind RPC to loopback or a trusted private network and keep cookie authentication enabled. For maintainers, startup validation, strict work budgets, pagination, and concurrency controls should make the dangerous configuration and the expensive methods difficult to misuse.
